# 1. PRD 的定位

PRD，全称 Product Requirement Document，即产品需求文档。

PRD 的核心不是描述“怎么实现”，而是明确：

- 要解决什么问题
- 给谁使用
- 本期做什么
- 本期不做什么
- 用户输入什么
- 系统输出什么
- 功能流程是什么
- 如何验收
- 异常情况如何处理
- AI 输出如何评估、追溯和兜底

---

## 1.1 PRD 应该回答的问题

| 问题 | 说明 |
|---|---|
| 用户是谁 | 明确目标用户和使用角色 |
| 用户痛点是什么 | 说明当前流程中的具体问题 |
| 功能目标是什么 | 明确本期要实现的能力 |
| 非目标是什么 | 明确本期不做什么，避免需求膨胀 |
| 输入是什么 | 自然语言、文件、URL、表单、JSON 等 |
| 输出是什么 | 文本、Markdown、JSON、报告、表格等 |
| 主流程是什么 | 从用户输入到结果输出的完整路径 |
| 如何验收 | 功能完成的判断标准 |
| 失败如何处理 | 检索失败、模型失败、证据不足等兜底策略 |

---

## 1.2 PRD 不应该直接回答的问题

以下内容更适合放在技术方案中，不建议在 PRD 中过早确定：

| 内容 | 原因 |
|---|---|
| 使用 LangGraph、CrewAI 还是自研工作流 | 属于技术选型 |
| 使用 PostgreSQL、MongoDB 还是 Elasticsearch | 属于存储架构 |
| 使用哪个 LLM 或 embedding model | 属于模型选型 |
| API 如何拆分 | 属于接口设计 |
| 数据库表结构怎么建 | 属于数据建模 |
| 代码类名、函数名怎么设计 | 属于代码实现 |

PRD 可以写“技术约束”，但不要把需求文档写成技术实现文档。

# 2. PRD 推荐结构

建议 Codex 默认按照以下结构生成 PRD。

```markdown
# PRD：{产品名称 / 功能名称}

## 1. 文档信息
## 2. 背景与问题
## 3. 产品目标
## 4. 非目标
## 5. 用户角色
## 6. 核心使用场景
## 7. 业务流程
## 8. 功能需求
## 9. 输入输出定义
## 10. AI 能力要求
## 11. 数据与来源要求
## 12. 非功能需求
## 13. 验收标准
## 14. 风险与边界
## 15. 待确认问题
```

# 3. 各章节写作规范

## 3.1 文档信息

### 目的

用于标识文档版本、状态、作者和关联材料，方便后续评审和迭代。

### 模板

```markdown
## 1. 文档信息

| 字段 | 内容 |
|---|---|
| 文档名称 | PRD：{功能名称} |
| 所属项目 | {项目名称} |
| 版本 | v0.1 |
| 状态 | 草稿 / 评审中 / 已确认 |
| 作者 | {作者} |
| 创建时间 | {YYYY-MM-DD} |
| 更新时间 | {YYYY-MM-DD} |
| 关联文档 | 技术方案 / 接口文档 / 测试用例 / 原型图 |
```

---

## 3.2 背景与问题

### 目的

说明为什么要做这个功能。

不要写空泛背景，例如：

> 随着人工智能快速发展，大模型应用越来越重要。

应该写具体业务问题，例如：

> 当前用户在进行行业研究时，需要手动搜索政策、公告、研报、新闻和企业披露信息，并自行判断来源可信度和证据有效性。该过程耗时长、可追溯性差、输出质量不稳定，因此需要构建搜索规划与证据链生成能力。

### 模板

```markdown
## 2. 背景与问题

当前 {目标用户} 在 {业务场景} 中，需要完成以下工作：

1. {用户当前要做的事情 1}
2. {用户当前要做的事情 2}
3. {用户当前要做的事情 3}

现有流程存在以下问题：

| 问题 | 具体表现 | 影响 |
|---|---|---|
| {问题 1} | {具体表现} | {业务影响} |
| {问题 2} | {具体表现} | {业务影响} |
| {问题 3} | {具体表现} | {业务影响} |

因此，本功能需要解决的核心问题是：

> {一句话总结核心问题}
```

---

## 3.3 产品目标

### 目的

说明本期功能要达到什么结果。

不要写：

> 提高效率，优化体验。

应该写：

> 支持用户输入自然语言研究问题后，系统能够自动完成问题拆解、搜索口径扩充、来源检索、证据抽取和结构化输出。

### 模板

```markdown
## 3. 产品目标

本期目标是构建 {功能名称}，支持用户完成：

1. {目标能力 1}
2. {目标能力 2}
3. {目标能力 3}
4. {目标能力 4}

功能完成后，用户应能够：

- 输入：{用户输入}
- 获得：{系统输出}
- 判断：{如何确认输出可用}
- 追溯：{如何查看证据或过程}
```

---

## 3.4 非目标

### 目的

控制需求边界，防止需求膨胀。

AI 项目尤其需要写清楚非目标，否则容易变成：

- 什么都想自动化
- 什么数据源都想接
- 什么报告都想生成
- 什么推理都想做
- 什么异常都想智能处理

### 模板

```markdown
## 4. 非目标

本期不解决以下问题：

1. 不做 {排除能力 1}
2. 不做 {排除能力 2}
3. 不做 {排除能力 3}
4. 不保证 {不承诺事项}
5. 不替代 {人工判断 / 专业审核 / 最终决策}
```

### 示例

```markdown
## 4. 非目标

本期不解决以下问题：

1. 不自动生成完整可发布的深度行业报告。
2. 不直接给出投资买卖建议。
3. 不接入全网所有数据源。
4. 不保证所有网页都能成功抓取和解析。
5. 不替代研究员对结论的最终判断。
```

## 3.5 用户角色

### 模板

```markdown
## 5. 用户角色

| 用户角色 | 说明 | 核心诉求 | 使用频率 |
|---|---|---|---|
| {角色 1} | {角色说明} | {核心诉求} | 高频 / 中频 / 低频 |
| {角色 2} | {角色说明} | {核心诉求} | 高频 / 中频 / 低频 |
| {角色 3} | {角色说明} | {核心诉求} | 高频 / 中频 / 低频 |
```

### 示例

```markdown
| 用户角色 | 说明 | 核心诉求 | 使用频率 |
|---|---|---|---|
| 研究员 | 使用系统进行行业研究 | 快速获得可信证据和初步结论 | 高频 |
| 审核人员 | 检查 AI 输出是否可靠 | 判断结论是否有证据支撑 | 中频 |
| 管理员 | 配置数据源、模型、规则 | 控制系统质量和稳定性 | 低频 |
```

## 3.6 核心使用场景

### 写作要求

每个使用场景必须包含：

- 用户是谁
- 在什么情况下使用
- 输入什么
- 系统需要做什么
- 输出什么
- 成功标准是什么

### 模板

```markdown
## 6. 核心使用场景

### 场景 1：{场景名称}

用户：{用户角色}

用户输入：

{示例输入}

系统需要：

1. {系统动作 1}
2. {系统动作 2}
3. {系统动作 3}

系统输出：

1. {输出内容 1}
2. {输出内容 2}
3. {输出内容 3}

成功标准：

- {成功标准 1}
- {成功标准 2}
- {成功标准 3}
```

## 3.7 业务流程

### 模板

```markdown
## 7. 业务流程

### 7.1 主流程

使用流程：

1. 用户输入请求。
2. 系统理解需求。
3. 系统拆解任务。
4. 系统执行核心处理。
5. 系统生成结构化结果。
6. 用户查看结果。
7. 用户反馈或修正。

### 7.2 流程说明

| 步骤 | 节点 | 输入 | 处理 | 输出 |
|---|---|---|---|---|
| 1 | 用户输入 | {输入} | 接收用户请求 | 原始请求 |
| 2 | 需求理解 | 原始请求 | 识别意图和约束 | 结构化需求 |
| 3 | 任务拆解 | 结构化需求 | 拆解子任务 | 子任务列表 |
| 4 | 任务执行 | 子任务列表 | 调用工具 / 检索 / 推理 | 中间结果 |
| 5 | 结果生成 | 中间结果 | 汇总、检查、格式化 | 最终输出 |
```

## 3.8 功能需求

### 功能需求总表

```markdown
## 8. 功能需求

| 模块 | 功能点 | 优先级 | 输入 | 输出 | 规则 | 验收标准 |
|---|---|---|---|---|---|---|
| {模块 1} | {功能点 1} | P0 | {输入} | {输出} | {处理规则} | {验收标准} |
| {模块 2} | {功能点 2} | P1 | {输入} | {输出} | {处理规则} | {验收标准} |
```

### 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | MVP 必须实现；没有它功能不可用 |
| P1 | 首个版本建议实现；影响体验或质量 |
| P2 | 后续优化能力；可以延后 |
| P3 | 可选能力；不影响主流程 |

### 单个功能详细模板

```markdown

|---|---|---|---|
| {字段名} | string | 是 | {字段说明} |

#### 输出

| 字段 | 类型 | 说明 |
|---|---|---|
| {字段名} | string | {字段说明} |

#### 处理规则

1. {规则 1}
2. {规则 2}
3. {规则 3}

#### 异常情况

| 异常 | 处理方式 |
|---|---|
| {异常 1} | {处理方式} |
| {异常 2} | {处理方式} |

#### 验收标准

1. {验收标准 1}
2. {验收标准 2}
3. {验收标准 3}
```

## 3.9 输入输出定义

### 写作要求

AI 应用必须明确输入输出，否则实现会失控。

需要说明：

- 输入是自然语言、文件、URL、JSON 还是表单
- 输出是普通文本、Markdown、JSON、报告、表格还是结构化对象
- 是否要求字段稳定
- 是否要求可被下游程序解析

### 模板

```markdown
## 9. 输入输出定义

### 9.1 输入

| 输入类型 | 示例 | 是否必填 | 说明 |
|---|---|---|---|
| 用户 query | {示例} | 是 | 用户自然语言请求 |
| 约束条件 | {示例} | 否 | 用户指定的数据源、时间、地区等 |
| 文件 | {示例} | 否 | 用户上传的 PDF、Excel、Word 等 |

### 9.2 输出

系统输出必须包含：

| 输出字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| summary | string | 是 | 输出摘要 |
| reasoning_dimensions | array | 是 | 分析维度 |
| evidence | array | 是 | 证据列表 |
| conclusion | string | 是 | 结论 |
| limitations | array | 是 | 局限性说明 |
| references | array | 是 | 引用来源 |
```

### JSON 输出示例

```json
{
  "summary": "string",
  "reasoning_dimensions": [
    {
      "name": "string",
      "description": "string"
    }
  ],
  "evidence": [
    {
      "claim": "string",
      "source_title": "string",
      "source_url": "string",
      "quote": "string",
      "confidence": "high | medium | low"
    }
  ],
  "conclusion": "string",
  "limitations": ["string"],
  "references": [
    {
      "title": "string",
      "url": "string",
      "source_type": "official | disclosure | report | media | unknown"
    }
  ]
}
```

# 4. AI 项目 PRD 特殊要求

普通软件 PRD 主要写页面、流程和功能。

但 AI Agent / RAG / 搜索规划 / 报告生成类项目，必须额外写清楚：

- AI 能力拆分
- 输出质量标准
- 证据链要求
- 兜底策略
- 可追溯机制
- 幻觉控制
- 成本和延迟边界

---

## 4.1 AI 能力要求

### 模板

```markdown
## 10. AI 能力要求

| 能力 | 说明 | 输入 | 输出 | 质量要求 |
|---|---|---|---|---|
| 意图识别 | 判断用户真正要解决的问题 | 用户 query | 意图类型、约束条件 | 常见场景识别准确 |
| 任务拆解 | 将复杂问题拆成多个子任务 | query + 意图 | 子任务列表 | 子任务不遗漏核心维度 |
| 搜索规划 | 生成可执行搜索词 | query + 子任务 | 搜索词列表 | 覆盖原始问题和扩展方向 |
| 信息筛选 | 判断搜索结果是否相关 | URL + 标题 + 摘要 | 相关性评分 | 排除明显无关结果 |
| 来源评级 | 判断来源可信度 | URL + 标题 + 正文 | 来源等级 | 官方来源优先 |
| 证据抽取 | 从正文中提取证据 | 文档正文 | 证据片段 | 证据必须支撑结论 |
| 结论生成 | 基于证据生成回答 | 证据集合 | 结构化结论 | 不输出无证据判断 |
| 质量检查 | 检查幻觉、引用、格式 | 初始输出 | 修正后输出 | 降低错误输出 |
```

---

## 4.2 AI 输出约束

```markdown
### AI 输出约束

系统必须遵守以下规则：

1. 不允许编造不存在的政策、数据、公司公告或来源。
2. 不允许把推断写成事实。
3. 关键结论必须绑定证据。
4. 证据不足时必须明确说明无法判断。
5. 输出中必须区分事实、推断和不确定项。
6. 对于时间敏感问题，必须保留信息发布时间或来源时间。
7. 对于来源可信度不足的问题，必须降低结论确定性。
```

---

## 4.3 数据与来源要求

### 模板

```markdown
## 11. 数据与来源要求

### 11.1 数据源类型

| 来源类型 | 示例 | 优先级 | 用途 |
|---|---|---|---|
| 官方政策 | 政府网站、部委网站、地方政府网站 | 高 | 政策依据 |
| 企业披露 | 年报、公告、交易所披露 | 高 | 企业事实依据 |
| 行业数据 | 统计局、协会、海关、能源数据 | 高 | 定量分析 |
| 研究报告 | 协会、研究机构、券商、咨询机构 | 中 | 行业观点参考 |
| 新闻媒体 | 财经媒体、地方新闻 | 中 | 事件补充验证 |
| 自媒体 | 公众号、论坛、博客 | 低 | 一般不作为核心证据 |

### 11.2 来源评级规则

| 等级 | 说明 | 示例 |
|---|---|---|
| A | 官方原文、企业正式披露、原始数据 | 政策原文、上市公司公告 |
| B | 官方新闻、发布会、权威新闻稿 | 政府新闻稿、官方发布会 |
| C | 解读、研究报告、协会报告 | 政策解读、行业协会分析 |
| D | 媒体转载、自媒体、二手信息 | 新闻转载、博客文章 |

### 11.3 证据要求

1. 每条关键结论至少绑定 1 条证据。
2. 证据必须包含来源标题、URL、发布时间、正文片段。
3. 证据片段必须能直接支撑对应结论。
4. 不允许使用无法访问或无法追溯的来源作为核心证据。
5. 多来源冲突时，需要标注冲突点，而不是强行合并。
```

## 4.4 非功能需求

### 模板

```markdown
## 12. 非功能需求

| 类型 | 要求 | 验收方式 |
|---|---|---|
| 性能 | 普通任务 P95 延迟小于 {阈值} 秒 | 压测或日志统计 |
| 稳定性 | 检索失败、解析失败、模型失败时有明确错误提示 | 异常用例测试 |
| 可观测性 | 记录 query、搜索词、工具调用、模型输入输出、错误日志 | 日志检查 |
| 成本 | 记录每次任务 token、模型调用次数、工具调用次数 | 成本日志 |
| 可追溯性 | 每条结论可以追溯到来源文档 | 抽样检查 |
| 可扩展性 | 数据源、模型、工具、Agent 节点可替换 | 代码评审 |
| 安全性 | 不输出无依据的高风险建议 | 安全测试 |
| 格式稳定性 | 结构化输出可被程序解析 | JSON schema 校验 |
```

# 5. 验收标准写法

## 5.1 写作原则

验收标准必须具体、可测试、可复现。

不要写：

> 系统可以正常使用。

应该写：

> 输入 10 个典型 query，系统能够生成有效搜索词，其中至少 8 个 query 的搜索词覆盖政策、企业、项目、数据等核心维度。

---

## 5.2 功能验收模板

```markdown
## 13. 验收标准

### 13.1 功能验收

| 用例编号 | 输入 | 预期输出 | 验收标准 |
|---|---|---|---|
```

# 7. 给 Codex 的生成要求

当使用 Codex 根据本参考文档生成具体 PRD 时，必须遵守以下规则。

---

## 7.1 生成原则

1. 先明确需求边界，再写功能。
2. 不要把 PRD 写成技术方案。
3. 不要在需求不明确时强行补全关键业务规则。
4. 可以合理补充工程常见字段，但必须标注为“待确认”。
5. 对 AI 功能必须写清楚输入、输出、质量要求、兜底策略。
6. 对 RAG、搜索、Agent 类功能必须写清楚证据链和可追溯要求。
7. 对每个 P0 功能必须给出验收标准。
8. 对不确定内容必须放入“待确认问题”，不要直接当作事实。

---

## 7.2 输出要求

Codex 生成的 PRD 应满足：

1. 使用 Markdown 格式。
2. 标题层级清晰。
3. 表格字段完整。
4. 功能点可拆分为开发任务。
5. 验收标准可转化为测试用例。
6. 风险项可转化为工程约束。
7. 待确认问题集中列出。
8. 不包含无意义的宣传性表述。

---

## 7.3 禁止行为

Codex 生成 PRD 时禁止：

1. 禁止只写概念，不写验收。
2. 禁止大量使用“智能化”“高效”“赋能”等空泛词。
3. 禁止把未确认技术选型写成确定方案。
4. 禁止把模型推断写成事实。
5. 禁止省略异常情况。
6. 禁止省略非目标。
7. 禁止省略 AI 输出质量评估。
8. 禁止默认所有数据源都可访问。

# 13. 推荐结论

适合 Codex 使用的 PRD 文档，不应追求形式复杂，而应优先保证：

1. 边界清晰。
2. 输入输出明确。
3. 功能可拆解。
4. 验收可执行。
5. 风险可识别。
6. AI 输出可评估。
7. 证据链可追溯。
8. 不确定项不乱补。

对于 AI Agent / RAG / 投研系统类项目，PRD 的关键不是“功能多”，而是：

> 输出是否可信，过程是否可追溯，失败时是否能兜底。
